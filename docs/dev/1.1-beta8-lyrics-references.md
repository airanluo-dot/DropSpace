# Windows 1.1 Beta 8 歌词与播放进度调研

核对日期为 2026-11-12。以下对照来自上游源码、项目手册和服务接口，覆盖 Windows 桌面歌词、播放器插件、跨平台歌曲匹配、歌词目录与音频指纹。上游案例说明一种实现需要什么输入。Beta 6 和 Beta 7 的差异、用户歌曲的失败原因和 Beta 8 的实际验证结果需要 DropSpace 自身的证据。

## 歌词数据库、目录 ID 与音频指纹

| 来源 | 查找输入、返回内容与边界 | 一手资料 |
| --- | --- | --- |
| LRCLIB 歌词接口 | `/api/get` 要求曲名和艺人，专辑、时长可省略。提供时长时，文档给出的容差是 ±2 秒。404 表示这组条件没有匹配。`/api/search` 支持指定曲名、艺人等字段，也支持跨字段的 `q`；带 `q` 时优先使用它，每次最多返回 20 条且无分页。因此宽泛查询的首屏也可能丢失正确版本。结果区分纯音乐标志、纯文本和同步歌词。 | [接口及响应定义](https://lrclib.net/docs) |
| AMLL TTML DB 歌词目录 | 同一条歌词可携带网易云、QQ 音乐、Spotify、Apple Music 等平台各自的曲目 ID，以及多个歌名、艺人或专辑元数据。已知当前平台与录音 ID 时可直接定位；跨平台需要显式映射，不能假定不同平台的相同数字属于同一首歌。 | [TTML 规范的元数据章节](https://github.com/amll-dev/amll-ttml-db/blob/main/instructions/ttml-specification-en.md#32-amll-metadata) |
| AcoustID / Chromaprint 音频指纹 | 接口接收从音频计算的指纹和整首时长，可返回关联的 MusicBrainz 录音及匹配分。Picard 的“扫描文件”实际采用这条路径。DropSpace 只从 SMTC 取得曲名、艺人和时间轴时缺少计算指纹所需的音频；即使认出录音，仍需另查歌词。 | [AcoustID 查询接口](https://acoustid.org/webservice#lookup) · [Picard 文件扫描](https://picard-docs.musicbrainz.org/en/latest/usage/retrieve_scan.html) |

## Windows 歌词怎样跟随进度

Microsoft 对 SMTC 的定义是，`Position` 对应 `LastUpdatedTime` 那一刻的进度，`PlaybackRate` 为 1 时表示正常速度。读取同一个样本两次，其 `Position` 可以相同。只有播放器发来可用的新样本，外部歌词程序才能确认真实进度或用户在播放器里执行的拖动。[时间轴字段](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessiontimelineproperties) · [播放速率](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessionplaybackinfo.playbackrate) · [时间轴变更事件](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssession.timelinepropertieschanged)

## 用这些案例判断 DropSpace 应改哪一层

- **搜索结果里找不到正确录音。** 对照原始 SMTC 字段与实际发送的词，检查是否缺专辑、把频道当艺人、丢掉合作艺人，或把附注作为必需关键词。在现有请求预算内比较字段查询、曲名查询或有依据的别名。检索放宽后仍用原来的艺人、版本和时长核验候选。[上游 LDDC](https://github.com/chenmozhijin/LDDC/blob/84631e8cd011fcc3f71ca0ae017e2c9758958ffc/LDDC/core/auto_fetch.py#L75-L156) · [DropSpace 曲名与署名规则](../../src/DropSpace.Core/Lyrics/LyricsMatcher.cs)
- **结果里有正确录音，界面仍然无词。** 依次核对候选是否通过录音验证、歌词请求是否取到正文、正文是否带时间、当时的源配置与截止时间、旧的无结果是否被重用。这能解释同样显示“无词”的不同故障，也能避免把一次超时写成曲库永久缺词。[OpenLyrics 搜索](https://github.com/jacquesh/foo_openlyrics/blob/3a3d95401beda70c02fe541ddcfe093d2a707f48/src/lyric_search.cpp#L126-L147) · [DropSpace 歌词查询服务](../../src/DropSpace.Infrastructure/Lyrics/LyricsService.cs)
- **歌词文本正确，显示先快后慢或停住。** 在同一次播放里对齐源、曲目、样本位置、更新时间、状态和速率，分别看“采样时的位置”“现在推算的位置”“实际选中的行”。重复样本只计算一次经过时间。暂停时冻结，收到可靠的 seek 后，从新位置重新找行。一次全局调快或调慢无法解释会来回变化的误差。[SMTC 时间轴](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessiontimelineproperties) · [DropSpace 播放时钟](../../src/DropSpace.Core/Media/MediaPlaybackClock.cs)
- **整首稳定早或晚、只在某个现场版出错。** 先核验录音版本及时间标记，再判断是否适合逐曲偏移。仅凭曲名、宽容阈值或指纹录音 ID 也无法保证歌词文件的行时间正确。[LyricsOnTheGo 逐曲偏移](https://github.com/The-MuffinDev/LyricsOnTheGo#features) · [AMLL 时间标记规范](https://github.com/amll-dev/amll-ttml-db/blob/main/instructions/ttml-specification-en.md)
