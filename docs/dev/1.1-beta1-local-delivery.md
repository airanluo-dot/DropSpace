# 1.1 Beta1 local delivery

Status: all four flows implemented, targeted verification completed, and a real self-contained
Windows x64 portable build produced and launched. Remaining manual coverage limits are listed below.
This is a local-only delivery;
no push, release tag, GitHub Release, asset upload, website or update-feed change is authorized.

## Scope and baseline

The four required flows are quick retrieval, opt-in new-file relay, reusable successful
outputs, and one user-opened reference window. They share existing DropItem identities,
the SQLite repository, clipboard/file transfer and native island. No whole-disk indexing,
third-party application adapters or background activation is introduced.

The repository release baseline was v1.0.0. Pre-existing untracked `.codex/` and
`scripts/__pycache__/` were left in place. The previous research conversations are
context; the complete user-supplied 1.1 plan is the acceptance contract. One referenced
research conversation exposes only a report placeholder, not its attachment body.

Repository publication instructions (merged-main promotion, public release verification,
website/feed publication) are out of scope for this delivery. The local UI label is
`1.1 Beta1`; machine metadata uses `1.1.0-beta.1`.

## Reference-window and lifecycle review record

The reference-window agent implemented `ReferenceWindowService` and `Views/ReferenceWindow.cs`:
one explicitly opened window shares the existing item ID, holds a recent-retention lease, replaces
its content on a new selection, and releases the lease on close. Its active-window timer checks
only the referenced object; passive changes never call `Activate`. Images use the existing bounded
preview and decoder validation, with zoom controls; text remains selectable and scrollable. The
existing preview limits remain 2 MiB for text, 25 MiB for encoded images and 100 million pixels;
the display decode is capped at 4,096 pixels wide. No reference window is restored at startup.

The same agent added 47 explicit App resource IDs in all ten supported languages and reviewed only
those IDs in the nine translated-language review records. The source manifest is
`artifacts/local-1.1-beta1/localization/new-ui-keys.json`. App localization integrity passed with
996 IDs across ten languages; `git diff --check` passed. Initial resource-review attempts included
one rejected `en-US` review (the tool accepts translated languages only) and one transient file-open
error; the scoped translated-language reviews subsequently completed. One App compilation found
two reference comparisons requiring `ReferenceEquals`; those two lines were corrected before the
primary agent's successful full compilation. These are build/resource evidence, not UI test passes.

Independent source review covered successful-output registration, cancellation boundaries, local
directory/internal-resource exclusion, and shutdown ordering. It found and corrected a completed
download's missing registration when its history checkpoint failed, and added `ItemActionRegistry`
shutdown draining so the app can await final output registration before closing recent storage.
It also identified `.dropspace-reservation` as a missing relay exclusion; the backend agent owns
that correction and its focused watcher validation.

`OutputRegistrationLifetimeTests` ran locally: **2 passed, 0 failed, 0 skipped**. The two scenarios
verify a hash-confirmed final download despite a failing completion checkpoint, and shutdown while
a committed action is still returning its result, including late cancellation and rejection of
new actions. Result: `artifacts/local-1.1-beta1/tests/output-registration-lifetime.trx`. This was the
only functional test group run by the reference-window agent; actual window, focus, image/text
rendering and desktop interaction evidence are owned by the primary agent's isolated runtime run.

If the recent-item database itself is unavailable after an output is committed, the external
output remains intact. Quick actions report registration failure; downloads preserve the completed
file and its download history and log the registration failure. There is no background reimport of
all previously completed downloads, which would resurrect records the user intentionally removed.

## Backend implementation, focused evidence and final integration review

Owner: `recent_backend`. The existing `DropItem`/SQLite repository now accepts `ItemSource.Recent`;
there is no second content store or database schema migration. `IRecentItemsService`,
`RecentItemsService`, `RecentFilePolicy`, `RecentItemMetadata` and the repository's `.Recent.cs`
partial own intake, shared metadata, availability and candidate retention. Settings persist the
explicitly selected directory list; its default is empty. Preservation promotes the same item ID
to Space, while pins and active reference leases protect candidates from expiry. Recent candidates
default to 30 days and 500 unprotected records. Stable new revisions refresh a Recent object's
candidate timestamp without changing the timestamps of ordinary Space or Clipboard objects.

The watcher admits only top-level Created/Renamed events, never imports an initial directory
inventory, and requires stable metadata observations and a readable file without a conflicting
writer. Temporary names, download reservation markers and identified DropSpace package/runtime/model
names are excluded. Explicit successful exports may use the existing app Exports directory; other
internal storage is excluded. Queue/pending capacity is 2,048, active metadata probes are capped at
64 per worker turn, and each selected directory keeps a single nonrecursive watcher. Watcher
overflow/unavailability is reported; recovery does not scan missed files into the content list.
Removal and retention delete records only, never external originals. Ordinary same-name files in
different directories retain separate IDs. Rename marks the former path missing and admits the
new path as a new reference; it does not silently rewrite the old reference.

Final integration review corrected four concrete boundaries: persisted waiting objects now resume
their availability checks after restart; pausing/removing a directory stops discovery while already
admitted waiting objects can settle; newly available replacements do not immediately expire using
the previous revision's old timestamp; and replacement by a directory or reparse point marks the
old file reference unavailable without changing its kind. Known file-change events mark the shared
object waiting before availability can be reused. Successful registration suppresses already queued
older watcher notifications and preserves path-based deduplication. Same-length/same-timestamp
overwrites observed by the watcher still invalidate the preview revision. Existing Clipboard
retention and owned-payload cleanup boundaries remain separate and unchanged.

All tests use isolated temporary directories and databases. They verify real files and ZIP entries,
not installed-user data or native UI behavior. Same-length writes may not emit a Windows LastWrite
notification until the writer closes; explicit retrieval/reference availability checks therefore
remain necessary. Content changed outside watched directories while preserving both size and
modification time cannot be detected from metadata alone until another observable file change;
there is intentionally no full-disk indexing or continuous file hashing. Database-unavailable
registration and OS watcher overflow preserve external files but may leave an undiscovered record;
the existing output/history and directory status remain the recovery evidence. Native focus, drag,
IME, reference rendering, final App compilation and packaged runtime evidence are owned by the
primary agent and are not claimed by these backend tests.

## Remaining verification limits and use

Physical Chinese IME candidate interaction, cross-application OLE transfer, and completing the
native folder picker were not verified. The picker opened in the earlier session but its separate
host was not targetable by the available UI helper. Directory selection/service persistence,
pause/resume and the resulting settings panel were verified separately. No full regression suite,
multi-monitor/DPI sweep, live music playback, or installed-user-profile upgrade was run. Background
tests assert unchanged foreground/page state; they do not imply a new music-playback certification.
Current image/ZIP/ordinary download producers output one final file per task; the common registration
contract handles multiple final paths and partial-success markers without adding a new batch UI.

For normal use, exit the already installed instance from its tray before opening the portable EXE.
Normal startup uses the existing `%LOCALAPPDATA%\DropSpace` configuration, as before; only the
explicit diagnostic command uses a new isolated profile. This delivery did not replace the installed
version, add startup registrations, push commits, create tags/Releases, upload assets, or change
public download/update/site content. Publication awaits new explicit authorization.
