# Beta4 glass background refresh investigation

Date: 2026-10-29. Owner: primary agent, no delegation. The first phase diagnosed
the delay without changing refresh behavior. The user then authorized timely
frame reception, discarding old frames, and a reopened test build, preserving
the original island UI. The implementation and measurements follow below.

## Evidence

One explicit 10-second moving-background probe in the Release review instance,
with real music active and blur 1 / refraction 100 / dispersion 75 / tint 0 /
Ink glass on. A compositor-driven striped window moved behind the topmost island.
The island was compact during sampling (443 x 50 pixels). Capture covered the
2560 x 1600 monitor; WMI reported its active mode as 240 Hz on AMD Radeon 880M.
An RTX 5080 Laptop GPU was also present; its presence does not establish which
adapter rendered this material.

Raw evidence: `artifacts/beta4/user-settings-review-02/refresh-20261029-072036.json`.

| Measurement | Result |

| Capture polls / consumed new frames | 295 / 295, no empty polls |
| Actual new background rate | 29.497 fps |
| Total material renders | 494, or 49.395 fps |

These are CPU wall times and consumed WGC timestamps. GPU execution duration,
power consumption, expanded-island performance and end-to-end photon latency
were not measured. Additional renders may reuse an old background frame and
must not be reported as a higher background refresh rate.

## Cause and limits

`LiquidGlassSurface` explicitly schedules a UI `DispatcherQueueTimer` at 30 Hz.
Its capture pool uses `Create`, two buffers, and each tick consumes only one
`TryGetNextFrame()` result. This establishes a 30 Hz background ceiling even on
the current 240 Hz display. The measured 29.5 fps closely follows that ceiling.
Reading only one queued frame instead of draining to the newest frame can add
staleness; the measured approximately 61 ms age is consistent with that path.
The experiment does not isolate how much of that age belongs to WGC internally.

`SetGeometry` can call `Render` between capture ticks, explaining why total draws
are higher than fresh captures. The current code also copies the entire monitor
texture before cropping to the island, and uses `Present(1)` on the UI thread.
These are potential future costs, but the short observed CPU submission times do
not support blaming them as the dominant cause in this compact-island sample.

The read-only WinIsland reference uses `CreateFreeThreaded`, a frame-arrived
notification and drains available frames to the latest. Its policy is not an
unlimited refresh-rate model: the inspected `system.rs` caps capture at 20, 30 or
60 Hz depending on integrated GPU and animation state. Reusing its general
fresh-frame strategy does not mean copying its GPL implementation.

Microsoft documents that [CreateFreeThreaded](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframepool.createfreethreaded)
removes the DispatcherQueue dependency and raises FrameArrived on an internal
worker thread. Its [screen-capture guidance](https://github.com/MicrosoftDocs/windows-dev-docs/blob/docs/hub/apps/develop/media-authoring-processing/screen-capture.md)
describes the QPC SystemRelativeTime and returning frame-pool buffers on disposal.

## Options presented after diagnosis

1. Recommended starting point: decouple capture from the UI thread, consume only
   the newest available frame, avoid duplicate renders, and target up to 60 Hz.
   Validate the actual cadence and frame age before considering the work complete.
2. The same architecture with an up-to-120-Hz target for smoother motion on this
   display. More frequent capture/copy/draw work is expected; battery/GPU cost and
   sustained achieved rate need measurement rather than a guarantee.
3. A smaller 60-Hz timer/latest-frame adjustment. Lower implementation scope, but
   capture and rendering remain exposed to UI-thread delays.

Simply changing 30 to 60 without addressing stale frames is not the recommended
fix. Any chosen implementation must retain the original island content, geometry,
hit targets, capture exclusion, hidden-state shutdown and fallback behavior.

## Authorized latest-frame implementation

`LatestGlassCapture` now owns a free-threaded WGC frame pool. Its worker callback
drains available frames and replaces one pending lease, disposing superseded
leases immediately. It posts no per-frame UI work and performs no D3D immediate
context or XAML operations. The UI owner takes only the latest lease, copies it
to its own GPU texture, and returns it to the pool before shader work or Present.
Thus copying/processing stays bounded by the existing render cadence rather than
running for every received frame.

The UI timer remains at 30 Hz. No shader, content, layout, geometry, controls,
settings or music behavior changed in this continuation. Capture-close callbacks
marshal to the UI owner with a generation check. Shutdown rejects callbacks before
disposing the pending lease/pool, outside the callback lock, to avoid a pool-close
deadlock. Measurements now separately count arrivals, replaced frames and the
age of the newest frame when consumed; counters are synchronized across threads.

Two 10-second moving-background probes ran in `user-latency-review-01`, with the
same material parameters and real music active. The second probe explicitly
collapsed the island to compare with the earlier compact measurement. Compact
width still follows live lyric content (old 443 px, new 368 px), so this is not
a pixel-identical workload or a GPU benchmark.

| Measurement | Previous compact | New compact | New expanded |
| --- | --- | --- | --- |
| New frames consumed / s | 29.497 | 29.400 | 29.398 |
| Frame age when consumed, mean | 61.424 ms | 9.475 ms | 9.306 ms |
| Frame age when consumed, p95 | 64.321 ms | 17.321 ms | 16.329 ms |
| Frame age when consumed, max | 69.812 ms | 20.938 ms | 22.771 ms |
| Worker-received frames | Not measured | 562 | 582 |
| Superseded pending frames discarded | None | 269 | 288 |
| Latest frame's wait after receipt, mean | Not measured | 8.891 ms | 9.509 ms |

The compact consumed-frame age dropped approximately 85% with essentially the
same consumption rate. This supports the old-frame backlog diagnosis. This metric
ends before GPU rendering/display and is not end-to-end screen latency. Arrival
timestamp differences occasionally straddle zero (expanded mean -0.192 ms); raw
QPC/compositor timestamps are retained rather than interpreted as negative latency.
