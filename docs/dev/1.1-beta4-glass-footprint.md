# Beta4 material resource footprint

2026-10-29. Primary agent only. User questioned a Task Manager screenshot showing
DropSpace at 1.4% CPU and 382.7 MB memory (20% CPU was the machine total).

## Method and observed cost

Read-only process CPU-time deltas were divided by elapsed wall time and this
machine's 20 logical processors. This differs from Task Manager's frequency-scaled
CPU utility. Memory is the process private working set. GPU utilization is the
busiest engine's integer counter sampled eight times, not a precise GPU-time or
power measurement. GPU shared-memory accounting can overlap system/process memory
and cannot be added to private working set. The driver, DWM and capture service
may have costs outside the app process.

The first same-process glass / acrylic / glass sequence, with real music active,
was confounded by ongoing lyric/content work, caching and time. CPU was
1.14 / 1.66 / 2.61%, and private working set 407 / 438 / 542 MiB. These samples
do not establish a material CPU/memory delta or prove a memory leak. Their raw
files are `artifacts/beta4/perf-before-{glass-1,acrylic,glass-2}.json`.

For a bounded material comparison, two fresh isolated diagnostic processes used
the same seed, visible settings window, static compact resident logo, and no
music initialization. Each warmed for ten seconds and sampled for about ten
seconds. Resident/logo were enabled only in these diagnostic seeds, not product
defaults or the user's retained review profile. Both exited normally.

| Fresh process | Acrylic | Glass before duplicate-draw fix |
| --- | --- | --- |
| CPU, percent of machine | 0.871 | 1.270 |
| Private working set | 136.37 MiB | 181.62 MiB |
| Committed private memory | 159.00 MiB | 209.82 MiB |
| Busiest GPU engine, sample mean | 0% | 0.75% |
| Shared GPU memory counter | 58.12 MiB | 139.03 MiB |

The short sample indicates approximately +0.40 CPU percentage points and +45.25
MiB private working set for glass in this scenario. It does not generalize to
every GPU, music workload, background, expanded island or long-running session.
The screenshot's full 382.7 MB cannot be attributed to glass alone.

Raw controlled results: `perf-fresh-acrylic.json`, `perf-fresh-glass.json`; exact
fixture state and clean exits: `footprint-before-acrylic/` and
`footprint-before-glass/` under `artifacts/beta4`. The read-only sampler is
`artifacts/beta4/Measure-GlassProcess.ps1`.

## Reference and remaining work

Read-only WinIsland source inspection confirms three existing optimizations:
region-limited GPU copies, checking whether pixels/dirty regions intersect the
island background before waking rendering, and a 20/30/60 Hz capture cap based
on integrated GPU and animation state. This is source evidence, not a runtime
benchmark comparing WinIsland and DropSpace. Its different runtime and feature
set prevent interpreting total process memory as a fair material-only benchmark.

DropSpace currently retains/copies a 2560 x 1600 BGRA monitor texture (about
15.6 MiB per full texture, plus WGC buffers) before cropping. A region-only cache
and background-change detection remain substantive optimization opportunities;
they must preserve fresh-frame behavior during movement, resizing and DPI changes.
They have not been implemented or claimed complete in this pass.

The implemented bounded optimization skips an identical material draw when the
background frame, shape/options, screen origin and panel dimensions are unchanged.
Movement and scale changes still render, even if the shape signature is equal.
No shader, optics, capture cadence, island UI or music behavior was changed.

## Bounded optimization result

Full Release App/XAML build passed with zero warnings/errors in 41.04 s
(`redundant-render-build.txt`). The equivalent fresh-process glass sample after
the duplicate-draw guard was 1.331% CPU, 183.42 MiB private working set and 1.0%
busiest-GPU-engine mean. This does **not** demonstrate a resource reduction from
the prior 1.270%, 181.62 MiB, 0.75% sample; the difference is within the limits of
these short, sequential, live-desktop measurements. The guard removes avoidable
work when identical layout notifications occur, but it does not reduce the full
monitor capture buffers or reliably solve the overall footprint concern.

Evidence: `perf-fresh-glass-after.json`, `footprint-after-glass/` (clean exit).
Tested GPU-support DLL SHA-256:
`7a87a3d892b3d47234a25af2899f5cd7d70f5cac93dedab60b89b75b002a0b61`.
The original settings and real music were restored in `user-performance-review-01`.
Its 10-second moving-background check skipped 39 identical draws, consumed new
frames at 29.30 fps and retained a mean frame age of 9.159 ms (p95 17.998 ms).
The material was ready without failure afterward. This proves that the guard
executes and preserves the measured low-latency path; it does not establish a
meaningful whole-process CPU/memory improvement. Island UI sources remain unchanged.
These results support revisiting the material cost before treating performance
work as complete; no default, fidelity, capture-rate or publication decision was
silently changed in response to the screenshot.

Microsoft documents GPU counter/shared-resource accounting in
[GPUs in Task Manager](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/).
Its [counter caveat](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/gpu-process-memory-counters-report-wrong-value)
also means an increasing GPU-process-memory counter alone is not leak proof;
no such leak conclusion is made here.
