## Evidence and implementation boundary

The user's local Dynamic Notch 2.0.3 (176) DMG has SHA-256
`55cdd608c0a9f56a3395bc93361715fdd6d830066cb9b71ca34f80bb17b69335`.
Its extracted `singerConfig.plist` contains one explicit artist mapping and 153
title pairs. The data resource records its own input hash and provenance. Native
Swift symbols, strings and disassembly establish bounded multi-candidate queries,
progressive best-result replacement, duration/timing quality and failure cooling.
The original Swift project and remote server implementation are unavailable.

DropSpace adapts these mechanisms in its existing C# pipeline. It does not import
proprietary executable code, private backend credentials or authenticated vendor
service configuration. The permissive Dynamic Notch fuzzy score is not an
admission rule: DropSpace retains complete artist-credit, version, language and
duration rejection. Short but valid songs receive no arbitrary ten-line penalty.

## Intended behavior and preserved contracts

- Bounded artist/title aliases enrich at most three queries while retaining raw
  metadata. Cross-language admission additionally requires duration evidence.
  Mappings containing extra featured/with credits cannot alone establish recording
  identity.
- Each online source compares up to six admitted candidates in its current pool.
  The first usable document remains progressive; the service's existing shared
  deadline, source allowlist, provider concurrency and stale-callback retirement
  still apply.
- Candidate quality is subordinate to admitted identity, target-language/native
  translation rules and configured source rank. Effective timed coverage must
  refer to real text and usable intervals.
- Endpoint health is bounded by provider and request stage. Manual refresh clears
  transient failures but preserves server rate limiting; cancellation and ordinary
  empty searches are not failures.
- Matcher/provider/cache identities advance where behavior changes. No settings
  schema, database, model bytes, CUDA component identity or visible UI resource is
  changed. AI remains opt-in and does not receive lyric bodies for selection.

## Document and code reconciliation

`ARCHITECTURE.md` described sequential preferred/backup execution, while the
existing service already used progressive supplemental lookup, a 150 ms backup
hedge and a bounded remaining-source quality window. Documentation follows the
verified callers and implementation; this change does not introduce unbounded
parallel searches.

`FEATURES.md` described tolerance of primary/full artist-credit lists. Existing
recording identity instead rejects missing collaboration credits and generic
minor title typos. Historical loose-match tests are not authority to weaken the
current complete-credit/title gate. Relevant current documentation is clarified.

Three selected legacy Infrastructure fixtures also fail on unchanged main
`a80940a34167da4cd5a8e2c45aa3e71ea17f4b4a`: an outdated QQ response fixture and two
fixtures expecting unrelated Latin artist names to enter weak AI selection. All
three identical failures were reproduced against that baseline using isolated
test outputs. Their assertions are not used to weaken the current identity or
transport contract; they remain separate baseline test debt.
