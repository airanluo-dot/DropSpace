# Windows 1.1 Beta 8 歌词排查

比较的是已发布的 [Beta 6](https://github.com/airanluo-dot/DropSpace/releases/tag/v1.1.0-beta.6)（`ae90426b`）和 [Beta 7](https://github.com/airanluo-dot/DropSpace/releases/tag/v1.1.0-beta.7)（`a70615c3`）。Beta 7 包含本地开发分支 `37a7ae23` 之后的发布修订，其中就有录音版本和 QQ 验证的变化。同类实现按检索、录音识别和播放同步整理在[上游案例](1.1-beta8-lyrics-references.md)。

## Apple Music Windows 双窗口实机复核

2026-11-12，在同一台电脑上同时读取 Apple Music 的播放条、Windows 媒体会话、日常版或独立修正版 DropSpace 的播放条，并在需要时分别抓取两个实际歌词窗。进度条以整秒比较。逐词则核对 DropSpace 此次真正选中的歌词原稿、用户偏移和窗口亮起的位置。两个平台可以采用不同分词和时标。

| 复现 | 查到的原因和结果 |
| --- | --- |
| 《...Baby One More Time》在音乐页只显示歌名 | 旧酷狗适配器读取总署名时丢失了同一艺人实体的中文名。用中文署名复现失败；核验目录里的完整署名和录音后，同一曲返回 58 行、335 个词级时间标记。Apple Music 重播时，日常版仍只显示标题，独立修正版已随播放显示原文。换成异人、只给姓氏、漏列合作艺人或指定另一场演出时仍拒绝错误候选。 |
| Adele 的《Rolling in the Deep》选到了不对应专辑的缓存 | 此机 Apple Music 把“艺人 — 专辑”同时放进艺人和专辑艺人，专辑字段为空。只对 Apple 的这种明确格式拆分查询，并让旧缓存按恢复的专辑重新验录音。在线实查选中网易《21》条目 2116996，61 秒和 66 秒取到正确的主唱行；《Thunder》原本与《Evolve》一致的缓存仍能离线读取。 |
| 《STAY》接入时 Apple 和 Windows 报 132 秒，旧时钟输出 134.30 秒 | 旧时钟把发布时间的年龄和固定的 1.5 秒补偿一起加到曲目位置。用同一段 94 个现场样本重放，修正后全都与 Apple 显示同一整秒。 |
| 《我们的歌》和《Outside》刚切入时，进度先走几秒又回零 | Apple 已报 Playing，但位置和曲长仍为零。旧实现最多自行走到 2.43 秒。修正后原先明显失准的 11 个样本均保持 Apple 的零位。正常播放在最近报告的整秒内插值，暂停冻结；发布方真正停止更新时恢复有标记的估算。 |
| 《STAY》0:57 两个窗口同一句，亮到的词不同 | 本轮修正版选中网易 1859306637。DropSpace 滑块位于 57.087、57.690、58.215、58.807 秒时，屏幕分别亮到该行第 3、4、7、11 词，四个位置都符合该文档。另一次播放用 Apple 的进程音频回环实测，Apple 显示刚跳到 0:57 时，音频已播到首次出声后约 58.18 秒。公开整秒读数和原生歌词画面之间的差异会随播放变化。 |
| 《Thunder》0:35，两边的进度读数和副歌高亮 | 本轮用了酷狗《Evolve》条目 165950780。实拍第一词收尾、第三词转第四词、第四词收尾的三张图，均符合选中文档的 35.398、35.759、36.360 秒边界。 |
| 网易 YRC 的零时长标点，以及增强 LRC 的首词 | 旧解析器将部分显式的零时长标记补到行尾。《STAY》中 20 个标记被延长，另一个行尾标记丢失。修正后保留原文的瞬时边界。回放《STAY》《Rolling in the Deep》和《Outside》的所测 YRC，原先的标点错误没有改变这三份文件中实际发声的选词。增强 LRC 中，行起点和第一个词标签间有正文时，首词现在从该行起点开始，重复行会平移同一份词级时间。 |

两曲共 1429 个可比较的实机采样，1399 个同秒。30 个相差一秒的样本均在下一次采样追平。其中 18 个是先读到 Windows 的旧秒，再读到 Apple 控件的新秒；另 12 个在外部监测读到 Windows 新秒时，DropSpace 的滑块还在上一秒。后者从系统发布时戳到首次确认界面追上的最长观测上界为 198 毫秒，不能从跨进程读取反推出精确的绘制耗时。Adele 的另一段复验中，43 张截图有 27 张可唯一判词，按选中文档和像素填充反算的位置与自身滑块的绝对差中位数为 48 毫秒。

录制器和离线逐词比对工具可单独运行。软件的播放进度、选词和绘制使用播放器报告、歌词原始时标与已有的用户手动偏移。[双进程监测](../../scripts/diagnostics/AppleMusicTimeline/README.md) · [双窗口逐词比较](../../scripts/diagnostics/AppleMusicLyricComparison/README.md)

## 本机到底遇到了哪种失败

11 月 12 日两份轮转日志中，按完整记录去重后共有 12 个歌词源阶段的终态。4 次找到歌词，4 次全部搜索失败，1 次完成搜索但未匹配，另 3 次是关闭或没有歌名。一次切歌可能产生多次请求，同一请求也会记录每个供应商的中间状态。这 12 条记录不能用于估计曲库命中率。

| 北京时间 | 从记录中能判断什么 |
| --- | --- |
| 14:17:22–14:17:59 | 四次源阶段失败。网易、酷狗、AMLL 和 LRCLIB 都在搜索阶段出现传输错误，没有 HTTP 状态码。此时改歌名相似度无法让服务返回候选。QQ 的请求另有本地拒绝记录。 |
| 14:22:11–14:22:50 | 网易连续找到四份歌词，分别有 50、48、40 和 57 行。 |
| 14:23:11 | 网易、酷狗、AMLL、LRCLIB 都完成查询且没有可用录音，QQ 被拒绝。即使一个源失败，其他源已完成的空搜索仍会显示“无匹配歌词”。日志没有请求曲名和原始候选，无法倒推出具体被拒绝的曲目。 |

Beta 7 的网络诊断不能区分 DNS、代理隧道、连接或 TLS 故障。Beta 8 在单个 HTTP 请求失败且没有 HTTP 状态时记录 .NET 报告的网络错误类别，沿用已有日志限额。普通日志不记录歌名、歌词正文、凭据或请求地址。

## 从系统曲目到歌词

1. Windows 媒体会话分别发布曲名、曲目艺人、专辑艺人、专辑和时间线。更换曲目会使旧查询失效；同一首曲目开始缺少时长、随后补足，在尚无歌词，或已有在线结果的录音时长缺失、与新时长不符时，会用新证据补查。可见窗口和灵动岛共用这条链。[Windows 会话](../../src/DropSpace.App/Services/Media/WindowsMediaSessionService.cs) · [媒体协调](../../src/DropSpace.App/Services/Media/MediaExperienceService.cs)
2. 本地 LRC 模式只读本地来源。在线模式普通重播先查缓存，使用曲目和时长、来源策略、翻译目标等信息定位文档，再检验录音身份、正文和来源数据版本。当前规则已确认且来源搜索完整的同步结果可以直接重播。可用但需要升级的旧缓存或纯文本会与获准的在线来源比较。需要联网时先等待元数据稳定（普通情况 400 ms，部分过渡状态 1.5 s）并联网。手动刷新可重新查询，仍遵守服务端限流。[歌词服务](../../src/DropSpace.Infrastructure/Lyrics/LyricsService.cs)
3. 先查首选源。可在首个有效原文出现时开始比较获准的补充来源；首选查空或失败后也可转入备用及其余已启用来源。备用源有 150 ms 的先行时间。每个源约 8 秒，全次查询上限 24 秒，证据完整且已有可同步正文后可以缩短比较窗口；只有纯文本或录音证据欠缺时，仍给已启用的备用源完成检索的机会。不同来源可以在同一请求内分别返回匹配、空目录、凭据拒绝或网络故障。[来源编排](../../src/DropSpace.Infrastructure/Lyrics/LyricsService.cs)
4. 适配器使用有界的曲名、艺人及别名检索，从目录记录取源内歌曲 ID。匹配器核对标题、完整演唱署名、录音与语言版本，再用专辑和时长佐证。标题检索可以较宽，显示前仍须检查录音身份。专辑艺人不能顶替已知的曲目艺人；同名的现场版、混音、翻唱和不同演出年份可能需要不同时间轴。[查询与匹配](../../src/DropSpace.Core/Lyrics/LyricsMatcher.cs)
5. 找到目录记录后，还需要取到同一记录的可用歌词，解析原文、逐行或逐字时间及翻译。空正文和占位文本会被淘汰；歌词源明确标记的纯音乐是另一种有效结果。首个合格文档可以先显示，随后按录音证据、可用同步时间、译文需求和来源偏好决定最终文档。当前播放代次校验会挡掉切歌后迟到的结果。可选 AI 翻译在原文搜索后运行。[文档选择](../../src/DropSpace.Infrastructure/Lyrics/LyricsService.cs) · [显示与翻译](../../src/DropSpace.App/Services/Media/MediaExperienceService.cs)

## 从播放器进度到当前歌词

Windows 把播放状态和时间线分开发布。会话层选择播放器及其可用的媒体会话，读取位置、开始、结束、播放速率和更新时间。时钟用这次观测建立锚点，在播放时根据单调时钟和速率推算两次上报间的位置，在暂停时保持当前位置。可见的播放界面约每 33 ms 读一次共享时钟。[Windows 时间线定义](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessiontimelineproperties) · [播放时钟](../../src/DropSpace.Core/Media/MediaPlaybackClock.cs)

时钟的位置是媒体坐标。渲染时先减去媒体开始位置，再施加用户设置的歌词偏移。歌词引擎用二分查找定位当前行，检查行的显式结束时间，并按词级起止时间求高亮比例。展开岛、紧凑岛和音乐视窗使用同一份帧；音乐视窗另有手动滚动和自动居中状态。只有整行时间的歌词不能提供原生逐字精度。歌词文件自身有固定偏移，也会在播放器时钟正确时显示早或晚。[帧计算](../../src/DropSpace.Core/Lyrics/LyricsModels.cs) · [呈现规则](../../src/DropSpace.Core/Lyrics/LyricsDisplayPolicy.cs) · [音乐视窗](../../src/DropSpace.App/Views/Music/MusicWindow.cs)

联网实查采用公开元数据 `Sunny Day / Jay Chou / Yeh, Hwei-Mei / 269 s`，未使用账号。生产歌词服务按首选网易、备用酷狗查询；网易完成搜索但没有匹配，酷狗返回《晴天》的 269.747 秒录音（ID `168513157`），43 行、565 个逐字或词片段，耗时 2.754 秒。这是一个跨语言曲名和备用源样本。上表的目录及会话故障用受控响应复现。夹具首次未设置最终响应 URI，被已有来源校验拒绝；补上 URI 后用同一输入比较修前、修后。

QQ 验证另重放了两种层级相同数字代表不同含义的响应。HTTP 200 携带业务 500 或业务 403 时保留此前连接，下一首仍能取词；带凭据的真实 HTTP 403 在这次显式验证中被标记为拒绝。业务 2001 仍标记过期，HTTP 429 仍进入冷却，冷却期间的下一次请求没有联网。

## 文档与运行行为

- [Beta 7 审查记录](beta7-windows-review-20261112.md)的 037、073 项说明了登录验证及版本标记的改进。发布代码却把未取得验证结论也当作会话拒绝，并对同年现场版的两种括号写法提取了不同标签。Beta 8 修正这两处实现，保留历史记录。
- [Windows 集成说明](../../WINDOWS_INTEGRATION.md)和网易增强的验证代码接受“位置合理前进、时间戳不变”，旧歌词时钟却在同一输入上重复加时。Beta 8 让歌词时钟使用新位置的实际读取时刻。
- [架构说明](../../ARCHITECTURE.md)原载歌词缓存范围为 100 MiB–5 GiB；设置策略和存储实现均为十进制 0–10 GB、默认 1 GB。已按实现修正文档。新版读取旧缓存键并重新核验录音和时标；可靠正文可在断网时保留，恢复联网后可升级文档。

## 优化后的回放

- 同一首《Die With A Smile》从原名、加 `(Official Audio)` 的标题、再切回原名，经真实 Windows 会话进入四处界面，均显示同步歌词。日语《夜に駆ける》的英文释名返回 56 行日语正文，英语重录另行匹配。仅有展示语言、曲名相同或时长接近时，仍需要录音证据。在线目录会随时间、地点和限流情况变化。
- 同名异人并列时保留歧义。目录中出现六条近似版本时，先核对能区分录音的证据再分配取正文的预算。已启用来源之间，弱录音不能抢占首屏；同一录音有带时间的正文时可以替换纯文本。用户得到的纯音乐标记只来自源对该录音的明确标识。
- 在固定目录中向真实媒体协调服务先送入无时长快照，再补报 200 秒；应用在紧凑岛、展开岛、媒体卡片和音乐视窗把先前的 330 秒版换成了 200 秒版。离线重播、弱旧缓存、混合源失败和全部查空分别回放。
- 同一公开 AMLL 文件在 208.600 秒重新高亮持续至 208.962 秒的主唱词。LRC 的正文件偏移会将行和词一起提前，显式间奏和 TTML 的重叠段分别保留。主唱和和声在各自时间区间内定位，使用同一时间索引选择当前行及预告行。
- 在 WinRT 测试播放器内播放起点已知的合成人声，进程音频回环检测到三次发声；四处歌词首次同时显示对应行与回环起点的首轮观测差为 +41、−30、+6 毫秒。加入已接受拖动的共用时钟后再跑一轮，观测差为 −44、−15、+40 毫秒；该轮 289 个有词采样中四处当前行均一致。界面约每 100 毫秒取样。这项测量包含软件播放、捕获与画面取样，无法推算蓝牙或扬声器到耳朵的延迟。
- 从 DropSpace 拖动时，三处进度条、当前句和高亮共用播放器已接受的目标。分别回放了迟到确认、拒绝、连续两次拖动、回包乱序、换曲及新样本矛盾。原生回放中，暂停后实际播放器已到 42.25 秒，Windows 十秒后仍报 13.63 秒；这段时间四处显示均保持 42.25 秒及对应行，用户仍可再次拖动。外部播放器内的跳转要等 Windows 发布新位置才能确认，实测一次暂停中的跳转在恢复播放前约 10 秒都没有新位置。
